# قواعد طراحی Nexora

این سند مرجع اجرایی طراحی رابط کاربری Nexora است. هدف آن یکدست نگه‌داشتن تجربه در Login، Workspace، گفتگو، Knowledge Base، Assistant، تنظیمات و بخش‌های مدیریتی است. هر تغییر رابط باید با این سند و توکن‌های موجود در کد هماهنگ باشد.

## جهت طراحی

Nexora یک فضای کاری دانش‌محور است، نه یک داشبورد تزئینی. رابط باید آرام، دقیق و قابل اعتماد باشد؛ محتوا و وضعیت عملیات در اولویت‌اند و رنگ بنفش فقط نقش تأکید و اقدام اصلی دارد. پاسخ‌های مبتنی بر RAG باید قابل پیگیری باشند و خطاها باید اقدام بعدی را روشن کنند.

اصول تصمیم‌گیری:

- یک اقدام اصلی در هر ناحیه وجود دارد؛ رنگ برند برای آن نگه داشته می‌شود.
- وضعیت، منبع پاسخ و خطا همواره نزدیک به همان عملیاتی نمایش داده می‌شوند که به آن مربوط‌اند.
- متن و دادهٔ کاربر، به‌ویژه فارسی، نام فایل و URL، نباید layout را بشکنند.
- سطح دسترسی باید در ناوبری و قابلیت‌ها بازتاب پیدا کند؛ گزینهٔ غیرقابل‌استفاده به کاربر نشان داده نشود.
- زیبایی بصری نباید کنتراست، خوانایی یا سرعت عملیات را قربانی کند.

## منبع حقیقت در کد

| موضوع | محل مرجع |
| --- | --- |
| رنگ، شعاع، تایپوگرافی و shadow | `frontend/app/src/styles/theme.css` |
| primitiveهای مشترک و responsive | `frontend/app/src/styles/design-system.css` |
| breakpointهای Tailwind | `frontend/app/src/index.css` |
| layout و رفتار drawer | `frontend/app/src/layouts/AppLayout.tsx` و `frontend/app/src/layouts/components/Sidebar.tsx` |
| صفحهٔ Login | `frontend/app/src/pages/LoginPage.tsx` و `frontend/app/src/styles/login.css` |

برای تغییر رنگ یا فاصله، ابتدا توکن یا primitive مشترک را بررسی کنید. از ساختن رنگ و فاصلهٔ مستقل در یک صفحه، مگر برای یک نیاز واقعاً محلی، خودداری کنید.

## رنگ و سطح‌ها

رنگ‌ها فقط با متغیرهای CSS استفاده می‌شوند. نام token باید معنای کاربردی را نشان دهد، نه رنگ خام.

| کاربرد | Light | Dark | Token اصلی |
| --- | --- | --- | --- |
| پس‌زمینهٔ برنامه | خاکستری آبی بسیار روشن | سرمه‌ای عمیق | `--surface-canvas` |
| سطح اصلی | سفید | آبی تیره | `--surface-panel` |
| سطح برجسته یا کنترل | روشن‌تر از canvas | تیره‌تر از panel | `--surface-raised` |
| متن اصلی | `#252c3e` | `#e7eaf3` | `--text-primary` |
| متن ثانویه | `#566177` | `#b3bfd2` | `--text-muted` |
| اقدام اصلی | بنفش کنترل‌شده | بنفش خوانا | `--brand-action` |
| موفقیت، هشدار، خطا | سبز، کهربایی، قرمز | نسخه‌های خوانای همان معنا | `--status-*` |

قواعد:

- از `--brand-action` برای CTA اصلی و حالت انتخاب‌شده استفاده کنید؛ بنفش نباید رنگ متن بدنه باشد.
- از رنگ به‌تنهایی برای انتقال وضعیت استفاده نکنید. متن، آیکون یا label وضعیت نیز لازم است.
- در Dark mode از بنفش روشن روی سطح روشن یا متن بنفش ریز استفاده نکنید. کنتراست متن عادی باید حداقل 4.5:1 باشد.
- Gradient فقط برای پس‌زمینه‌های غیرتعاملی، hero Login و تأکیدهای محدود مجاز است؛ کنترل‌ها باید سطحی پایدار و خوانا داشته باشند.

## تایپوگرافی و زبان

فونت رابط انگلیسی `Inter` و فونت فارسی `Vazirmatn` است. محتوای فارسی با `dir="rtl"` و `--font-fa` نمایش داده می‌شود؛ نام فایل و رشته‌های ترکیبی فارسی/لاتین از `unicode-bidi: plaintext` بهره می‌برند.

| نقش | اندازه |
| --- | --- |
| عنوان صفحه | 20 تا 28px |
| عنوان بخش یا کارت | 14 تا 18px |
| متن بدنه | 13 تا 14px |
| متن کنترل و metadata | حداقل 12px |
| input و textarea در موبایل | حداقل 16px |

قواعد:

- اندازهٔ متن کاربردی کمتر از 12px نباشد.
- line-height متن فارسی حداقل 1.6 و برای پاسخ‌های چندخطی 1.7 تا 1.9 باشد.
- متن توضیحی مهم از رنگ `--text-muted` استفاده می‌کند و نباید تنها با opacity پایین ساخته شود.
- برای متن قابل‌شکستن از `.nexora-text-wrap` استفاده کنید.
- برای نام فایل، عنوان محدود و مقدارهای طولانی از `.nexora-file-name` استفاده کنید. در دسکتاپ ellipsis و در موبایل حداکثر دو خط نمایش داده می‌شود.

## فاصله، ابعاد و شکل

مقیاس فاصله ثابت است: 4، 8، 12، 16، 24 و 32px (`--space-1` تا `--space-6`). فاصلهٔ دلخواه مانند 13 یا 19px فقط در صورت نیاز بصری مشخص قابل قبول است.

- ارتفاع کنترل عادی: 40px (`--control-height`).
- هدف لمس در موبایل: حداقل 44×44px (`--touch-target`).
- شعاع کنترل: 8px؛ پنل: 12px؛ dialog: 14px.
- پنل‌ها با border ظریف و `--shadow-panel` از پس‌زمینه جدا می‌شوند. shadow تیره یا سنگین برای کارت‌های عادی استفاده نشود.
- محتوای صفحه از `.nexora-page-frame` با `--page-gutter` و حداکثر عرض `--content-max` استفاده می‌کند.

## کامپوننت‌های پایه

### دکمه و اقدام

از `.nexora-action` استفاده کنید. variantهای مجاز `--primary`، `--secondary` و `--danger` هستند. دکمهٔ disabled باید `disabled` واقعی داشته باشد، نه فقط opacity. دکمهٔ آیکونی باید `aria-label` و در موبایل هدف لمس 44px داشته باشد.

### وضعیت و بازخورد

از `.nexora-status` با variantهای `info`، `success`، `warning` و `danger` استفاده کنید. پیام خطا باید سه بخش داشته باشد: چه عملی ناموفق بود، اثر آن چیست و کاربر چه کاری می‌تواند انجام دهد. امکان Retry نزدیک خطا قرار می‌گیرد.

### بارگذاری و پردازش

برای عملیات طولانی، مرحلهٔ فعلی، درصد یا نشانهٔ پیشرفت و اقدام لغو یا Retry در صورت امکان نمایش داده شود. spinner عمومی `.nexora-loader` است. در پاسخ گفتگو، وضعیت تفکر ساده، کوتاه و قابل لغو باقی می‌ماند.

### Empty state

Empty state فقط نبود داده را اعلام نمی‌کند؛ باید اقدام بعدی را روشن کند. نمونهٔ اصلی: در نبود Knowledge Base، CTA ساخت مجموعه و بارگذاری نخستین سند نمایش داده می‌شود.

### Dialog و Drawer

Dialog باید `role="dialog"`، `aria-modal="true"`، نام قابل‌خواندن و دکمهٔ بستن داشته باشد. با بازشدن، focus به نخستین کنترل معنادار منتقل می‌شود؛ Tab در آن محصور می‌ماند و Escape آن را می‌بندد. پس از بستن، focus به trigger بازمی‌گردد. Drawer سایدبار در موبایل همین قرارداد را دنبال می‌کند و محتوای پشت آن inert می‌شود.

## تجربهٔ RAG

نزدیک هر پاسخ یکی از وضعیت‌های زیر نمایش داده شود:

- **پاسخ مستند:** منبع مرتبط از Knowledge Base پیدا شده است.
- **پاسخ ترکیبی:** پاسخ از منبع و دانش عمومی مدل شکل گرفته است.
- **پشتوانهٔ ناکافی:** منبع مرتبط یا پوشش کافی پیدا نشده است.

کاربر باید بتواند منبع، نام فایل، صفحه یا بخش، و در صورت وجود امتیاز retrieval را باز کند. Share و Feedback در Dialogهای قابل‌دسترسی نمایش داده می‌شوند. کپی موفق فقط پس از موفقیت Clipboard API اعلام می‌شود.

## Responsive

قرارداد breakpoint پروژه:

| بازه | عرض |
| --- | --- |
| Mobile کوچک | 320 تا 479px |
| Mobile بزرگ | 480 تا 767px |
| Tablet | 768 تا 1023px |
| Laptop | 1024 تا 1439px |
| Desktop عریض | 1440px به بالا |

در عرض کم:

- Sidebar به Drawer بسته‌شونده تبدیل می‌شود.
- پنل Knowledge assistant تمام‌عرض یا bottom sheet است.
- toolbarهای چندستونه به ستون یا منوی بیشتر تبدیل می‌شوند.
- فهرست‌ها و جدول‌ها یا اسکرول افقی کنترل‌شده دارند یا به کارت خلاصه تبدیل می‌شوند.
- input و textarea حداقل 16px هستند تا Safari هنگام focus zoom نکند.

قبل از ادغام هر تغییر رابط، نماهای 320، 375، 390، 768، 1024 و 1440px را بررسی کنید.

## دسترس‌پذیری

- همهٔ کنترل‌ها با Tab، Shift+Tab، Enter و Space قابل استفاده باشند.
- `:focus-visible` واضح و سازگار با theme باشد؛ focus را صرفاً با `outline: none` حذف نکنید.
- label واقعی یا `aria-label` برای input، دکمهٔ آیکونی و select الزامی است.
- dialog و drawer با Escape بسته شوند و focus trap داشته باشند.
- `prefers-reduced-motion: reduce` باید animation و transition غیرضروری را حذف یا کوتاه کند.
- متن، آیکون و رنگ وضعیت باید با هم استفاده شوند؛ رنگ تنها نشانهٔ خطا یا موفقیت نیست.
- تغییر theme نباید hero Login را تغییر دهد؛ hero در Light و Dark ثابت می‌ماند.

## حرکت و تعامل

حرکت باید بازخورد بدهد، نه نمایش. سرعت پیش‌فرض `--transition-fast` برابر 160ms است. hover می‌تواند حداکثر یک جابه‌جایی 1px داشته باشد. برای عملیات در حال پردازش از انیمیشن ممتد پرنور، لرزش یا skeleton طولانی استفاده نکنید. کاربر دارای کاهش حرکت باید تجربهٔ کامل اما بدون حرکت غیرضروری دریافت کند.

## چک‌لیست تغییر رابط

- آیا از token و primitive موجود استفاده شده است؟
- آیا متن فارسی، نام فایل بلند و URL بدون overflow نمایش داده می‌شوند؟
- آیا Light و Dark هر دو کنتراست کافی دارند؟
- آیا کنترل موبایل 44px و field تایپی 16px است؟
- آیا حالت loading، empty، error و disabled طراحی شده‌اند؟
- آیا Tab، Escape، focus trap و `prefers-reduced-motion` بررسی شده‌اند؟
- آیا نقش کاربر فقط گزینه‌های مجاز را می‌بیند؟
