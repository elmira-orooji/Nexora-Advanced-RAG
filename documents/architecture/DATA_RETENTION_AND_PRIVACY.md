# نگه‌داری داده و حریم خصوصی Nexora

این سند محدودهٔ داده‌های Nexora، محل نگه‌داری آن‌ها، حذف و دوره‌های پیشنهادی نگه‌داری را تعیین می‌کند. این یک سند فنی و عملیاتی است و جایگزین تصمیم حقوقی، قرارداد پردازش داده یا مشاورهٔ حقوقی نیست. پیش از استفادهٔ سازمانی، مالک محصول باید دوره‌های پیشنهادی را با الزامات قراردادی و قانونی سازمان تأیید کند.

## اصول اجرایی

- داده فقط برای ارائهٔ قابلیت انتخاب‌شده، امنیت، پشتیبانی و ادارهٔ سامانه پردازش می‌شود.
- دادهٔ یک سازمان باید از طریق `organization_id` و کنترل‌های مجوز مجموعهٔ دانش از سازمان‌های دیگر جدا بماند.
- دسترسی عملیاتی به متن اسناد، گفتگوها، رمزها یا secretها باید محدود، ثبت‌شده و فقط برای نیاز مشخص باشد.
- حذف در محصول به معنی حذف از دادهٔ عملیاتی است؛ نسخه‌های پشتیبان تا پایان دورهٔ نگه‌داری backup باقی می‌مانند.
- داده‌های حساس نباید به لاگ‌ها، ابزار مشاهدهٔ خطا، تیکت‌ها یا محیط توسعه منتقل شوند.

## داده‌های ذخیره‌شده و محل آن‌ها

| دسته | نمونه | محل نگه‌داری اصلی | هدف |
| --- | --- | --- | --- |
| هویت و عضویت | نام کاربری، عنوان شغلی، نقش، hash رمز | PostgreSQL | ورود، کنترل دسترسی و مدیریت تیم |
| نشست | شناسهٔ نشست، زمان انقضا و ابطال | PostgreSQL و cookie امن مرورگر | حفظ نشست کاربر |
| اسناد آپلودی | فایل اصلی، متن استخراج‌شده، checksum و metadata | document storage و PostgreSQL | دانش سازمان |
| بردارها | بردار chunk، شناسهٔ سند و metadata بازیابی | Qdrant | جست‌وجو و پاسخ مبتنی بر منبع |
| Connector | URL منبع، وضعیت sync، metadata و شناسهٔ خارجی | PostgreSQL و document storage | همگام‌سازی منبع مجاز |
| گفتگو و پاسخ | پیام‌ها، منابع پاسخ، پاسخ ثبت‌شده و بازخورد | PostgreSQL | تاریخچه و بهبود پاسخ |
| اشتراک گفتگو | snapshot پیام‌ها، token hash، تاریخ انقضا | PostgreSQL | اشتراک‌گذاری کنترل‌شده |
| مصرف مدل | مدل، tokenها، زمان پاسخ و هزینهٔ تخمینی | PostgreSQL | تحلیل مصرف و عملیات |
| اعلان | نوع رخداد، عنوان، متن و وضعیت خوانده‌شدن | PostgreSQL | اطلاع‌رسانی درون‌محصولی |
| دادهٔ امنیتی | شمارندهٔ تلاش ورود و لاگ ردشدن آپلود | PostgreSQL و log sink | جلوگیری از سوءاستفاده و بررسی رخداد |

Nexora فقط hash رمز عبور را در پایگاه‌داده نگه می‌دارد. Secretهای Connector برای providerهای ابری از secret manager سازمان دریافت می‌شوند و نباید در جدول Connector، لاگ یا خروجی diagnostic ذخیره شوند.

## انتقال داده به سرویس‌های بیرونی

وقتی OCR ابری فعال است، فایل یا محتوای لازم برای استخراج ممکن است به provider انتخاب‌شده ارسال شود. وقتی مدل زبانی بیرونی استفاده می‌شود، پرسش کاربر و context بازیابی‌شده برای تولید پاسخ به provider مدل ارسال می‌شود. فعال‌سازی هر provider باید با نیاز سازمان، محل پردازش داده، سیاست provider و قرارداد مربوط سازگار باشد.

در محیطی که انتقال داده به بیرون مجاز نیست، OCR ابری و مدل بیرونی نباید فعال شوند، مگر آن‌که مسیر پردازش و قرارداد داده به‌صراحت تأیید شده باشد.

## سیاست نگه‌داری و اجرای آن

دوره‌ها باید پیش از استقرار production با الزامات قرارداد و قانون سازمان تطبیق داده شوند. پاک‌سازی خودکار به‌صورت پیش‌فرض خاموش است تا داده‌ای بدون تأیید مسئول محیط حذف نشود. با فعال‌سازی `DATA_RETENTION_ENABLED=true`، document worker در بازهٔ `DATA_RETENTION_MAINTENANCE_SECONDS`، رکوردهای عملیاتی منقضی را به‌صورت یک تراکنش حذف می‌کند. دورهٔ هر دسته نیز با متغیرهای `DATA_RETENTION_*_DAYS` قابل تغییر است.

| داده | دورهٔ پیش‌فرض | حذف، بازیابی و مالک اجرا |
| --- | --- | --- |
| حساب فعال و تنظیمات عضویت | تا زمان حذف عضو یا سازمان | حذف طبق درخواست مدیر و بررسی وابستگی‌های مالکیت |
| نشست منقضی یا ابطال‌شده | ۳۰ روز | purge خودکار پس از انقضا/ابطال؛ مسئول عملیات مقدار آن را تنظیم می‌کند |
| فایل و متن سند فعال | تا حذف توسط مدیر یا پایان قرارداد | فقط حذف صریح مدیر، همراه با chunkها و بردارها؛ restore فقط از backup هم‌دوره |
| chunk و embedding | تا حذف سند یا بازسازی index | با حذف سند ابتدا Qdrant و سپس metadata و storage پاک می‌شود؛ در بازیابی، از snapshot Qdrant یا پردازش مجدد سند بازسازی می‌شود |
| فایل ردشده در قرنطینه | ۷ روز، فقط اگر `MALWARE_RETAIN_DETECTED` فعال باشد | بازبینی و حذف توسط مسئول امنیت؛ نگه‌داری طولانی‌تر فقط با نیاز بررسی رخداد |
| job پردازش موفق | ۹۰ روز | نگه‌داری خلاصهٔ عملیاتی؛ حذف پس از تأیید مدیر محیط |
| job شکست‌خورده یا dead letter | ۹۰ روز پس از رفع/بستن رخداد | حذف پس از بررسی علت و ثبت نتیجه توسط مسئول عملیات |
| پیام و گفتگو | تا حذف گفتگو توسط کاربر مجاز یا دورهٔ سازمان | حذف خودکار ندارد؛ سیاست سازمان باید مسیر حذف و restore را تأیید کند |
| Chat share منقضی یا لغوشده | ۳۰ روز | purge خودکار snapshot و token hash پس از پایان دوره |
| بازخورد و evaluation case | ۱۲ ماه | ناشناس‌سازی یا حذف طبق سیاست سازمان |
| اعلان خوانده‌شده | ۹۰ روز | purge خودکار؛ اعلان خوانده‌نشده حفظ می‌شود |
| LLM usage و هزینه | ۱۲ ماه | purge خودکار جزئیات؛ در صورت نیاز مالی فقط دادهٔ تجمیعی مصوب نگه‌داری شود |
| لاگ امنیتی و رد آپلود | ۹۰ روز | چرخش فایل با `LOG_MAX_BYTES` و `LOG_BACKUP_COUNT`؛ retention log sink مسئول محیط است |
| نسخهٔ پشتیبان | مطابق `documents/operations/BACKUP_AND_RECOVERY.md` | حذف خودکار پس از پایان retention backup |

## حذف سند و همگام‌سازی حذف

حذف سند در API فقط برای مدیر همان سازمان مجاز است. روند فعلی تلاش می‌کند بردارهای سند را از Qdrant حذف کند، رکورد PostgreSQL را حذف کند و سپس پوشهٔ فایل در storage را پاک کند. اگر پاک‌سازی storage موفق نشود، پاسخ API وضعیت `storage_removed` را منعکس می‌کند. این مورد باید در عملیات پیگیری شود تا فایل باقی‌مانده بدون مرجع نماند.

حذف سند به‌دلیل حذف از یک مجموعهٔ دانش با حذف کامل سند متفاوت است. اگر سند همچنان عضو مجموعهٔ دیگری باشد، نباید از storage یا Qdrant حذف شود. حذف یک Connector نیز باید بررسی کند که سندهای حاصل از آن منبع، هنوز در مجموعهٔ دیگری استفاده نمی‌شوند یا نه.

دادهٔ حذف‌شده ممکن است تا زمان انقضای نسخه‌های پشتیبان باقی بماند. بازیابی backup پس از درخواست حذف می‌تواند دادهٔ قدیمی را بازگرداند؛ در چنین بازیابی‌ای، حذف‌های ثبت‌شده پس از زمان backup باید دوباره اعمال شوند.

## حذف عضو و سازمان

حذف عضو توسط مدیر انجام می‌شود و حساب مدیر در مسیر فعلی قابل حذف نیست. به‌دلیل وابستگی‌های مالکیت، حذف کاربر ممکن است مسدود شود؛ برای نمونه وقتی کاربر مالک منبع اشتراکی است. در این وضعیت، ابتدا مالکیت یا منبع وابسته باید به عضو مناسب منتقل یا حذف شود.

حذف کامل سازمان هنوز نباید به‌صورت حذف دستی و مستقیم در پایگاه‌داده انجام شود. پیش از افزودن این قابلیت باید یک جریان کنترل‌شده داشته باشد که موارد زیر را به‌ترتیب اجرا و گزارش کند:

1. تأیید مدیر سازمان و کنترل هویت او.
2. لغو نشست‌ها، Chat shareها و دسترسی Connectorها.
3. حذف اسناد، chunkها، بردارهای Qdrant و فایل‌های storage.
4. حذف رکوردهای وابستهٔ PostgreSQL با رعایت constraintها.
5. ثبت شناسهٔ درخواست و زمان پایان حذف، بدون نگه‌داری متن محتوا.

## دسترسی، صادرات و درخواست داده

- کاربر فقط باید دادهٔ متعلق به سازمان خود و مجموعه‌های دانش مجاز را ببیند.
- export داده باید همان محدودهٔ مجوز UI و API را رعایت کند و فایل خروجی نباید در مسیر عمومی یا دائمی نگه‌داری شود.
- درخواست مشاهده، اصلاح یا حذف داده باید شناسهٔ درخواست، محدودهٔ داده، تأیید هویت و نتیجهٔ اجرا داشته باشد.
- برای داده‌ای که حذف آن با الزام قانونی، امنیتی یا backup در تضاد است، محدودیت باید شفاف و همراه با تاریخ بازبینی ثبت شود.

## کنترل‌های فنی مرتبط

| کنترل | وضعیت در پروژه |
| --- | --- |
| جداسازی سازمان | `organization_id` در موجودیت‌های اصلی و کنترل‌های API |
| حذف session هنگام logout | session در پایگاه‌داده revoke و cookie حذف می‌شود |
| انقضای share | `expires_at` و امکان revoke در Chat share وجود دارد |
| حذف سند | حذف از Qdrant، PostgreSQL و تلاش برای پاک‌سازی storage |
| قرنطینهٔ فایل | فایل پیش از پذیرش در quarantine اسکن و سپس promote می‌شود |
| محدودسازی secret | Connector credential از secret manager سازمان دریافت می‌شود |
| encryption | باید در سطح storage، PostgreSQL، Qdrant، backup و TLS محیط استقرار اعمال و مستند شود |
| purge زمان‌بندی‌شده | session، Chat share، اعلان خوانده‌شده و LLM usage با فعال‌سازی صریح retention اجرا می‌شود |

## وظایف دوره‌ای مدیر محیط

ماهانه، مدیر محیط باید نتیجهٔ metric با نام `nexora_retention_records_deleted_total`، dead letterها، فایل‌های قرنطینه، shareهای منقضی و رشد backup را بررسی کند. هر سه ماه، دوره‌های نگه‌داری، providerهای فعال و دسترسی‌های عملیاتی بازبینی شوند. هر تغییری در دوره‌های نگه‌داری یا provider پردازش داده باید در این سند و تنظیمات deployment ثبت شود.
